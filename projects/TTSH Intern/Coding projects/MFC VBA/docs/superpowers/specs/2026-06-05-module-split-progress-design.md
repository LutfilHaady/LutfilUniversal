# MFC Report — Module Split + Progress Window

**Date:** 2026-06-05
**Status:** Draft (pending review)

## Background

A company AI agent will be set up for FC staff to chat with when they need to
read, debug, or adjust the MFC macro. That agent has **strict file-size /
context limits**, and the current `BuildOutput.bas` (793 lines, 15 procedures
doing ~5 distinct jobs) is too large to feed it cleanly. The goal is to split
the oversized modules into smaller, single-purpose files — **meaningfully
smaller, each one job, all under ~200 lines** — while keeping the explanatory
comments that make them readable.

Separately, staff cannot see the macro's progress: it runs with
`ScreenUpdating = False` and never pumps the message queue, so the
`Application.StatusBar` step text never repaints. This spec adds a visible
**progress-bar window** instead.

Note on source files: every VBA module lives both as an individual file
(`.bas` / `.frm`, the working copy the agent reads) and concatenated inside
`MFC_All_Modules.txt` (a transfer convenience, regenerated by
`regen_modules.ps1`). **Both must be kept in sync for every change.**

## Goals

- Break the two oversized modules along natural responsibility seams so each
  file is ~200 lines or fewer and has one clear job.
- Cut dead code to reduce total context.
- Add a visible progress-bar window driven by the existing 9 macro steps.
- Keep all comments and **all runtime behaviour and output identical** (this is
  a restructuring, not a feature change).

## Non-goals (out of scope)

- No change to filtering, lookup, carry-forward, dropdown, or output logic.
- No change to the output column layout (A–P) or the report contents.
- No change to the file-selection dashboard (`FilePickerForm`).
- No automated tests (no VBA test harness exists).

- `LoadPreviousMFC`, `ApplyCarryForward` → stay with `BacklogSummary` in `Backlog.bas`.

## Feature 3: Progress-bar window (`ProgressForm`)

### Why

`MainMacro` sets `Application.StatusBar = "Step N/9: ..."` before each step, but
the bar never visibly updates because the run holds `ScreenUpdating = False` and
the message queue is never pumped. Replace the invisible StatusBar text with a
visible modeless progress window.

### `ProgressForm.bas` (NEW)

A code-built UserForm using the same runtime-control pattern as
`FilePickerForm` (controls created in `UserForm_Initialize`, so there is no
`.frx` binary to manage). Stored as `ProgressForm.bas` in the repo to match the
existing `FilePickerForm.bas` convention (the regen script and the agent read
`.bas`). Like `FilePickerForm`, the file begins with the UserForm
`VERSION 5.00 / Begin … End / Attribute` header so it imports as a form.

Controls (built in code):
- A title/step caption label (e.g. "Step 3 of 9 — Extracting admission dates…").
- A bar "track" (a sunken Frame or Label spanning the form width).
- A bar "fill" (a coloured Label inside/over the track whose width =
  trackWidth × stepNum / totalSteps).

Public interface:

```vba
Public Sub ShowProgress(totalSteps As Long)   ' build/reset, Show vbModeless
Public Sub Update(stepNum As Long, message As String)  ' set caption + fill width + Me.Repaint
Public Sub CloseProgress()                    ' Unload / Hide
```

Behaviour:
- `ShowProgress` stores `totalSteps`, resets the fill to 0 width, and shows the
  form **modeless** (`Me.Show vbModeless`) so `MainMacro` keeps executing.
- `Update` sets the caption, sets the fill width proportionally, and calls
  `Me.Repaint` to force an immediate redraw even while `ScreenUpdating = False`.
- `UserForm_QueryClose` cancels a manual close (`vbFormControlMenu`) so staff
  cannot accidentally dismiss the window mid-run (same guard pattern as
  `FilePickerForm`).
- `StartUpPosition` centred; always-on-top is not required.

### `MainMacro.bas` wiring

- Declare and show the form at the start of `GenerateMFCReport`:
  ```vba
  Dim prog As New ProgressForm
  prog.ShowProgress 9
  ```
- Before each of the 9 steps, **replace** the existing
  `Application.StatusBar = "Step N/9: ..."` line with:
  ```vba
  prog.Update N, "<same step text>"
  ```
- In `Cleanup`, close the form:
  ```vba
  On Error Resume Next
  prog.CloseProgress
  On Error GoTo 0
  ```
  (guarded, since `Cleanup` runs on both success and early exit).
- Keep `Application.StatusBar = False` in `Cleanup` (harmless; clears any
  residual bar text). The per-step `Application.StatusBar = "..."` assignments
  are removed in favour of `prog.Update`.

This keeps `MainMacro` roughly the same length and changes no step logic.
